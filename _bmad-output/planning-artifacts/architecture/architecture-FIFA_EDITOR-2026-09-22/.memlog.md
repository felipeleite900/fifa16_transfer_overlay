- (constraint) [ADOPTED] fifa_overlay e crate unico e plano: lib.rs (598 linhas, entry point DLL + ImguiRenderLoop::render) + memscan.rs + fifa_db.rs + pointer_scan.rs. Sem mod.rs aninhado, sem config.rs/state.rs ainda.
- (constraint) [ADOPTED] Render loop hoje e um unico metodo render() com um unico ui.window(), crescendo por blocos sequenciais dentro do mesmo closure. NAO existe sistema de abas/rotas/screens separadas - maior lacuna a resolver para a Central de Scout (4 abas + telas satelite).
- (version) hudhook 0.9.3 (feature dx11), imgui 0.12.0, windows 0.62.2 (Win32_Foundation/Memory/Threading/Diagnostics_Debug/ProcessStatus), memchr 2.8.3, tracing 0.1.44 + tracing-subscriber 0.3.23 + tracing-appender 0.2.5. profile.release com debug=true.
- (constraint) [ADOPTED] Padrao de tarefa assincrona repetido 3x: enum EstadoX{Idle,Running,Done{...}} + Arc<Mutex<EstadoX>> + Arc<AtomicBool> _in_progress, spawn via std::thread::spawn, leitura do resultado sempre dentro de bloco { } proprio para dropar o MutexGuard antes de qualquer &mut self subsequente. NUNCA scan pesado dentro de render() diretamente.
- (constraint) [ADOPTED] Sem nenhuma persistencia em disco hoje alem do log (tracing-appender grava em %TEMP%/fifa_overlay.log via std::env::temp_dir()). Sem serde/toml/dirs no Cargo.toml. Precisa ser adicionado para o arquivo de estado do Scout.
- (constraint) [ADOPTED] Error handling: zero unwrap/expect/panic no crate overlay (so no injector CLI, aceitavel ali). Padrao let-else com Option em vez de panic, .get(a..b) em vez de indexacao direta de slice, .lock().ok() em vez de .lock().unwrap(), toda leitura de memoria via ReadProcessMemory/WriteProcessMemory protegido (nunca deref de ponteiro Rust cru).
- (constraint) [ADOPTED] Nomenclatura: snake_case funcoes/campos, PascalCase structs/enums, sufixo _state para enums de estado assincrono, sufixo _in_progress para AtomicBool, prefixo spawn_*_thread. Comentarios de modulo (//!) em portugues explicando o porque. Logging via tracing::info!/warn! com tag de origem entre colchetes.
- (constraint) [ADOPTED] Mundo Python/Electron (companion/, fifa_process_identifier/) e mundo Rust (fifa_overlay/fifa_injector) sao 100% separados, sem nenhuma ponte IPC/FFI/subprocess hoje. Logica de scout tera que ser reimplementada em Rust dentro do fifa_overlay, seguindo o padrao ja usado por fifa_db.rs (reimplementacao Rust de partes de fifa16_db_parser.py).
- (decision) Paradigma de telas: Enum de tela + dispatch. Um enum ScoutScreen (ou similar) guardado no estado da Central de Scout; render() principal faz match e chama uma funcao de render por tela/superficie, cada uma em seu proprio arquivo/modulo dentro de um novo diretorio scout/. Navegacao = trocar o valor do enum guardado na struct. Menor salto de complexidade a partir do padrao atual (unico closure), mapeia 1:1 com a Information Architecture do EXPERIENCE.md (4 abas + Ficha de Jogador + Formulario Nova Missao + Painel de Selecao Geografica + Confirmacao de Contratacao).
- (decision) Limite de modulo: novo modulo fifa_overlay/src/scout/ com submodulos: mod.rs (ScoutScreen enum + dispatch), screens/ (uma tela por arquivo: olheiros.rs, missoes.rs, relatorios.rs, sonar.rs, ficha_jogador.rs, nova_missao.rs, selecao_geografica.rs, confirmacao_contratacao.rs), state.rs (structs de dominio: Olheiro, Missao, Relatorio, Jogador encontrado), persistence.rs (ler/escrever arquivo de estado do Companion), quality.rs (formulas de Qualidade/Fit Posicional/similaridade - podem comecar como stub, formulas exatas deferidas). Modulos existentes (memscan, fifa_db, pointer_scan) permanecem como infraestrutura de leitura de memoria, consumidos pelo scout/ sem duplicacao. Rejeitado crate separado - fifa_overlay e fifa_injector nao sao um workspace Cargo hoje, adicionar um terceiro crate exigiria configurar workspace, complexidade desnecessaria para o escopo hobby.
- (decision) Timing da busca: computar SO na conclusao. Na criacao da Missao, apenas os criterios de filtro sao persistidos (nenhum scan roda ainda). Quando o painel e reaberto e a checagem de data (GJUr.currdate) indica que o prazo estimado passou, o scan real contra a memoria atual (CZUM/elenco/mundo) e disparado naquele momento, refletindo o estado mais recente do jogo. Consistente com EXPERIENCE.md State Patterns ja existente: progresso e recalculado a cada abertura do painel, nao em tempo real - mesmo gatilho (abertura do painel) agora tambem dispara a execucao real da busca quando devida.
- (decision) Generalizacao de tarefa assincrona: criar tipo generico AsyncTask<T> (provavelmente em memscan.rs ou novo async_task.rs na raiz de src/) encapsulando o trio Arc<Mutex<TaskState<T>>> + Arc<AtomicBool> ja usado 3x no codigo (scan de DB, pointer scan, value scan). Vira uma regra formal (AD): toda nova operacao assincrona do Scout (execucao de busca de missao, escrita de contratacao, leitura de elenco) deve usar esse tipo generico em vez de copiar o padrao a mao. Investimento pequeno agora evita repeticao maior com a chegada de multiplas operacoes assincronas novas.
- (decision) Concorrencia entre missoes: execucao SEQUENCIAL - quando multiplas Missoes vencem o prazo ao mesmo tempo (usuario ficou tempo sem abrir o painel), sao processadas uma apos a outra numa fila simples, nunca scans paralelos simultaneos. Prioriza previsibilidade e menor uso de CPU/memoria simultaneo sobre velocidade total, adequado ao escopo hobby V1.
- (decision) Formato/local do arquivo de estado: JSON via serde + serde_json (novas dependencias no Cargo.toml do fifa_overlay - nenhuma delas existe hoje). Local: %LOCALAPPDATA%\\FifaCompanion\\ - sobrevive a limpezas de %TEMP% e reinicios do PC, ao contrario do padrao atual do log (std::env::temp_dir()).
- (decision) Escopo do arquivo: UM ARQUIVO POR SAVE, nomeado pelo hash da pasta do save (mesmo hash ja usado em Documents\\FIFA 16\\0\\FIFA16\\<hash>\\DATA). Caminho: %LOCALAPPDATA%\\FifaCompanion\\scout\\<hash_do_save>.json. Isso RESOLVE diretamente a Questao em Aberto #5 do PRD (troca de save com missoes pendentes) - elimina o cenario de conflito por design, ja que cada save tem seu proprio arquivo isolado; nao ha mais necessidade do aviso 'ver mesmo assim/descartar' assumido no EXPERIENCE.md, que pode ser removido/simplificado na proxima atualizacao do UX.
- (decision) Fronteira scout <-> memscan/fifa_db: nova camada fina de repositorio, save_repo.rs (raiz de src/, paralelo a memscan.rs/fifa_db.rs), expondo funcoes de alto nivel no vocabulario de dominio (ex: read_squad_players() -> Vec<Player>, write_transfer_budget(new_value) -> bool, read_current_date() -> Date). Regra de dependencia: scout/ so pode chamar save_repo, NUNCA memscan/fifa_db diretamente - so save_repo.rs toca memscan/fifa_db. Isola o dominio do Scout de detalhes de bit-packing/offset binario, e concentra num unico lugar qualquer mudanca futura na forma de ler memoria (ex: se pointer-chains de atributo por jogador forem resolvidas algum dia).
- (question) Investigado: NAO existe campo dedicado de ID unico de save/carreira acessivel via memoria - confirmado ausente tanto no codigo/docs do projeto quanto nas 137 tabelas do metadata real do FIFA 16 (fifa_ng_db-meta.xml). EA trata identidade do save via sistema de arquivos (pasta-hash), nao via campo interno.
- (decision) Estrategia de ID de save: pseudo-ID composto via MEMORIA (nao arquivo), formado por GJUr.startdate (data de criacao da carreira, campo mapeado no metadata mas AINDA NAO lido/validado - mesma tecnica ja usada para GJUr.currdate) + mPrV.firstname/surname (nome do manager) + mPrV.clubteamid (time controlado). Motivo de rejeitar a alternativa de arquivo: a heuristica do fifa16_search.py (pasta mais recente por mtime) so atualiza no SALVAMENTO, nao no CARREGAMENTO - cenario de falha real: usuario carrega save antigo sem salvar nesta sessao, mtime aponta erroneamente para outro save mais recentemente salvo. Isso e um risco de correcao SILENCIOSA (aponta pro save errado com confianca), pior que o risco de colisao improvavel do pseudo-ID. Pseudo-ID via memoria reflete o estado real do processo em execucao, nao uma inferencia externa sujeita a corrida.
- (question) GJUr.startdate precisa ser validado (lido e confirmado como constante ao longo de multiplas sessoes na mesma carreira) antes de confiar nele em producao - nunca testado ainda, mesmo estando mapeado no metadata XML. Candidato a primeira tarefa tecnica de validacao na implementacao.
- (decision) Fronteira sync/async no save_repo: regra explicita por tipo de operacao. Leituras de campo unico ou tabela PEQUENA (read_current_date, read_transfer_budget, read_squad_players - elenco do usuario e pequeno, ~30 jogadores, mPrV/GJUr sao registro unico) sao SEMPRE sincronas, chamadas direto dentro de render() sem thread - custo desprezivel. Qualquer operacao que varra CZUM INTEIRA (~32k jogadores) - ou seja, a execucao de busca de uma Missao aplicando os 5 filtros do FR-4 - e SEMPRE assincrona via AsyncTask<T>, nunca chamada direto no render(). A assinatura da funcao em save_repo.rs (fn sincrona normal vs fn que retorna/dispara um AsyncTask<T>) torna a distincao auto-evidente no codigo, sem exigir julgamento caso a caso.
- (decision) Navegacao aninhada: pilha de telas via Vec<ScoutScreen> no estado do Scout. Abrir uma tela = push, voltar = pop. Suporta qualquer profundidade de aninhamento futuro sem logica especial - voltar e sempre a mesma operacao (pop) em qualquer lugar do app.
- (decision) Politica de escrita do arquivo de estado: WRITE-THROUGH - toda mutacao de estado (contratar olheiro, criar missao, arquivar relatorio, etc) dispara escrita imediata e sincrona do arquivo JSON inteiro (poucos KB, custo desprezivel). Estado em memoria e em disco nunca divergem por mais que um instante - elimina risco de perda de dados em crash do jogo com o painel aberto.
- (decision) Scan em progresso ao fechar painel: CONTINUA rodando em background. Fechar o painel de Scout so esconde a UI (o AsyncTask sobrevive independente do ciclo de vida da tela) - a thread de scan roda ate terminar naturalmente e grava o resultado via write-through no arquivo de estado. Proxima abertura do painel ja encontra o resultado pronto.
- (decision) Onde vive a logica de filtragem: scout/search.rs (novo modulo, separado de quality.rs). save_repo.rs expoe SO dados brutos (ex: read_all_players() -> Vec<PlayerRaw>), sem saber o que e um filtro ou uma missao. Toda logica de aplicar os 5 filtros do FR-4 (geografico, overall/potencial, atributo dominante, fit posicional, jogador de referencia) + calculo de Qualidade/Fit/similaridade vive dentro de scout/search.rs e scout/quality.rs, nunca no save_repo. Mantem save_repo como camada burra de acesso a dados; logica de dominio do Scout fica 100% concentrada dentro de scout/.
- (decision) Contrato de erro do save_repo: toda funcao publica retorna Result<T, SaveRepoError>. SaveRepoError e um enum com variantes tipadas (ex: TabelaNaoEncontrada, ProcessoInacessivel, CarreiraNaoCarregada). O scout/ trata cada variante explicitamente e decide a UI correspondente (CarreiraNaoCarregada -> estado vazio do EXPERIENCE.md; ProcessoInacessivel -> mensagem de erro com opcao de retry). Erro tipado permite UI diferenciada por causa, nao um erro generico unico.
- (decision) Concorrencia entre AsyncTasks diferentes: MULTIPLAS AsyncTasks concorrentes sao permitidas. Cada preocupacao (execucao de busca de missao, leitura de elenco para Seletor, etc) tem seu proprio AsyncTask<T> independente, podem coexistir sem bloquear uma a outra. A regra de execucao SEQUENCIAL ja decidida vale apenas ENTRE missoes que vencem o prazo ao mesmo tempo (mesma fila de execucao de missao), nao é um lock global do Scout inteiro.
- (decision) Paradigma nomeado formalmente: Arquitetura em Camadas (Layered). 4 camadas: UI/Screens (fifa_overlay::scout::screens) -> Dominio (fifa_overlay::scout - state, search, quality, persistence) -> Repositorio (fifa_overlay::save_repo) -> Infraestrutura (fifa_overlay::memscan, fifa_overlay::fifa_db). Regra mestra (vira AD-1): dependencia estritamente unidirecional de cima para baixo - uma camada so pode chamar a camada imediatamente abaixo dela, nunca pular camadas nem depender de uma camada acima. Todas as decisoes anteriores desta sessao (scout so chama save_repo nunca memscan direto, save_repo so expoe dados brutos sem logica de filtro, etc) sao instancias concretas dessa regra mestra.
- (decision) Formato de ID das entidades: UUID v4 (nova dependencia: crate uuid, feature v4+serde). Cada Olheiro/Missao/Relatorio/Jogador-encontrado recebe um UUID gerado na criacao. Missao referencia olheiro_id (UUID), Relatorio referencia missao_id (UUID). Nunca colide, nao depende de contador sincronizado, estavel mesmo apos arquivamento/remocao de registros.
